钱：0=不花钱 / 少=几十到几百 / 多=上千或长期支出

毅力：否=做一次就完 / 些=改个习惯 / 是=长期对抗惯性
收益：大 / 中 / 小（按阈值从收益栏机械套）

受益人四档

① 你自己 → ② 配偶和直系亲属 → ③ 朋友同事和其他亲属 → ④ 陌生人。

06可迁移到自己项目的 6 条方法

不管你写的是代码、文档还是知识库，这个项目的核心答案都一样：把「可信」翻译成 CI 能通过的检查项。

METHOD 01
位置依赖的引用，必须记内容不记位置

「见第 8 条」这种只记条号的引用，插入一条就集体错位，而顺延后的条号通常仍在范围内， 查越界一条都抓不到。解法：把每个引用解析成它实际指向的标题写进对照表入库， git diff 直接把错位摆出来。

METHOD 02
给 AI 的输出定「机器可判定」的禁写清单

「别写得 AI 味太重」不是可执行的规则；「说人话不许出现 HR/RR/OR、不许超过 120 字、 不许出现收益栏里没有的数字」才是。写不出检查项的规范，等于没有规范。

METHOD 03
质量检查不挡发布，除非它真的该挡

四个质量 job 故意独立、不挂 build：锚点没补好不该连累电子书发布。 PR 上照样红，main 上该发的还是发出去。门禁的严厉程度要和故障代价匹配。

METHOD 04
规则文件里不写会跟着内容漂的数值

SKILL.md 里不留节的清单、不留档位阈值——要用就去读 README 的表和 index.html 的两行代码。 增删节、改规则都不用动规则文件本身。单一数据源的另一种解法：全部改成运行时读取。

METHOD 05
把「我凭什么这么想」写成结构化字段

成本 / 收益 / 证据等级 / 原始出处四个字段，把一条建议从「观点」变成「可核对的记录」。 再补一条：有争议时把反方证据也贴上——全书 88 条主动标注争议，这是它最硬的地方。

METHOD 06
允许「做不到」，但不许含糊
